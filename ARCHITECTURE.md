# Архитектура Isoliner3D: ядро, инструменты, сцена

Документ описывает переход модуля к архитектуре из трёх уровней.
Первый уровень: модуль QGIS в новой архитектуре (ветка 1.5.0).
Второй: сцена как отдельное приложение на Rust. Третий: та же сцена
и те же инструменты внутри RustGIS. Образец раскладки на крейты
взят из PlanetX Lite (`crates/` и `apps/`).

## Слои модуля

| Слой | Где лежит | Знает QGIS и Qt |
|---|---|---|
| Ядро расчётов | `mesh3d.py`, `iso3d.py`, `fill.py`, `sweep.py`, `boolean3d.py` и ещё три десятка модулей | нет |
| Инструменты | `toolspec.py`, пакет `tools/` | нет |
| Обёртка QGIS | `algorithms.py` (`SpecAlgorithm` и прежние классы), `provider.py` | да |
| Сцена: данные | `scenes.py`, `scene_package.py`, `gltf.py`, `flight.py`, `axes.py` | нет |
| Сцена: окно | `viewer_dialog.py`, `viewer3d.py` | да |

Правило одно: стрелки идут только вниз. Ядро не знает инструментов,
инструменты не знают QGIS, окно не знает Processing.

## Инструмент как объект

Инструмент состоит из описания и расчёта (`toolspec.py`).

Описание (`Tool`): код («2.23»), имя Processing, название, группа,
справка и поля (`Param`). У поля ключ, вид, подпись, подсказка,
значение по умолчанию, пределы, пункты списка, родительский слой.
Виды полей: `mesh` (весь слой одним телом), `meshes` (тело на объект),
`lines`, `points`, `table` (таблица или слой: атрибуты и первая
вершина), `features` (объекты любой геометрии: вершины частей),
`raster` (растр: `Grid`), `band` (номер канала растра-родителя),
`field`, `string`, `bool`, `number`, `integer`, `enum`
(с `multiple` - несколько пунктов), `sink`. Признак `advanced`
уводит поле в дополнительные параметры. Необязательный выход
приходит в `run` признаком, заказан ли он. К каждому слою обёртка
добавляет `values["@КЛЮЧ"]`: имя слоя, род геометрии, есть ли Z,
имена полей, числовые поля. Выход с `geometry="line"` - линии с Z,
`geometry="point"` - точки с Z, тип поля `copy:КЛЮЧ` переносит поле
слоя с его типом: так 2.18 пишет интервалы со всеми полями таблицы.

Выход с `geometry="source"` возвращает объекты источника с их
же геометрией: так устроен отбор 2.12. Выход с `replace` пишет
свои поля в одноимённые поля источника, значения объекта тогда -
словарь {поле: значение}: так 2.14 перезаписывает поля прошлого
прогона.

Растр приходит в `run` объектом `Grid`: привязка шестью числами
в порядке GDAL, число каналов, форма, подписи каналов, метаданные
и система координат строкой WKT. Канал берётся `grid.band(номер)`
с единицы, массивом float, пусто - NaN. Обёртка читает каналы
по запросу, поэтому многоканальный грид не грузится целиком ради
двух каналов. Без QGIS `Grid` собирается из списка массивов. У слоя
растра `values["@КЛЮЧ"]` несёт имя, `geometry: "raster"`, число
каналов и их подписи. Выход растром - поле `sink` с
`geometry="raster"`, `run` отдаёт для него `RasterResult(Grid, имя)`.
Обёртка пишет GeoTIFF Float32 с пустым NaN, подписями каналов
и метаданными, система координат - у `Grid` или от первого входа.
В `tools.json` и образцах растр - объект с `transform`, `names`,
`meta` и `bands` (строки ячеек, пусто - `null`).

Расчёт: функция `run(values, report)`. На входе простые данные:
тело `{"verts", "faces"}`, линии и точки списками словарей, числа,
номера пунктов. На выходе словарь `{ключ выхода: Result}`. Сообщения
идут через `report` шаблоном с аргументами, ошибка расчёта - через
`ToolError`. Строки для пользователя помечены `N_()`, переводит их
обёртка при показе.

Обёртка `SpecAlgorithm` одна на все такие инструменты. Она строит
поля Processing по описанию, читает слои в простые данные, вызывает
`run` и пишет `Result` в слои. Класс инструмента в `algorithms.py`
сводится к имени, названию и строке `SPEC = "имя"`. Имя и название
остаются в классе строками: по ним панель Processing, проверки AST
и сборщики руководства и страницы находят инструмент. Совпадение
класса и описания стережёт `test_spec_tools_match_their_classes`.

`tools/export_tools.py` выгружает описания в `tools.json`: каждая
строка на двух языках, формат файла с номером. Этот файл читают
приложения без Python.

### Перенос остальных инструментов

Сейчас объектами стали 2.11, 2.12, 2.13, 2.14, 2.17, 2.18, 2.23
и 2.24. Остальные 24 переходят по одному, порядок такой:

1. Расчёт из `_process` переезжает в `tools/<имя>.py` функцией
   `run`, подсказки и справка в описание теми же русскими строками.
   Переводы в `i18n.py` подходят без правки.
2. Класс в `algorithms.py` становится наследником `SpecAlgorithm`.
3. Тест в `tests/test_tools.py` гоняет `run` на простых данных
   и сверяет с ядром, как `test_sweep_matches_the_module`.
4. Проверка в QGIS: тот же прогон, что до переноса, итог тот же.
   Скрипты `tools/qgis_check/run_2xx.py` гоняют инструмент в QGIS
   без окна, провайдер подключается прямо из папки пакета, профили
   QGIS не трогаются. Запуск дважды, с прежним пакетом и с новым,
   затем сравнение JSON: поля, значения, геометрия, журнал, отказы.

       python-qgis.bat tools/qgis_check/run_214.py <папка> <выход.json>

   Папка - та, где лежит пакет `isoliner3d`: корень хранилища или
   копия прежней сборки.

Первыми шли инструменты на телах и линиях (2.11, 2.12, 2.14, 2.17,
2.18). Вид поля `raster` и выход растром появились вместе с 2.13,
дальше идут инструменты на растрах и кубах. Демонстрационные (1.07,
1.08, 2.01, 2.09, 2.16, 2.19, 2.22) переносятся последними: им нужен
вид выхода «набор слоёв».

## Сцена отдельно от QGIS

Окно держит сцену в проекте QGIS: состояние ссылается на слои по id,
геометрия строится из слоёв при каждом открытии. Приложению без QGIS
нужна сцена, где геометрия уже собрана. Это пакет `.i3dscene`
(`scene_package.py`), его пишет окно через «Выгрузить сцену».

Пакет - zip из двух файлов.

`scene.glb` - геометрия, как в выгрузке GLB: настоящие высоты, план
сдвинут на круглую точку начала, привязка в `asset.extras.isoliner3d`.

`scene.json`:

| Ключ | Что |
|---|---|
| `format` | наименьший формат, которым пакет читается: 1 без точек, 2 с точками. Пакет новее читателя не читается |
| `module`, `version` | кто записал |
| `name` | имя сцены |
| `crs` | `authid` и `wkt` системы координат |
| `origin` | точка начала плана в GLB |
| `vex` | преувеличение по вертикали в окне |
| `camera` | камера в настоящих координатах: `center`, `distance`, `azimuth`, `elevation`, `fov`, `ortho` |
| `views` | виды облёта, как камера |
| `parts` | части сцены: `node` в GLB, `name`, `kind` (`mesh`, `lines` или `points`), `decor`, `layer`, `shape`, размеры |
| `glb` | имя файла геометрии |
| `state` | полное состояние окна QGIS, для возврата в проект |

Точки векторных слоёв (пробы, значки) и линии (борозды) идут
в пакет так, как нарисованы в окне (`viewer_core.vector_export_parts`),
часть на слой. Круглые значки - примитив POINTS в GLB, у каждой
точки цвет `COLOR_0` и размер в пикселях экрана `_SIZE` (своё имя
атрибута с подчёркиванием, чужие просмотрщики его пропускают).
`shape` у такой части `circle`. Квадраты, ромбы, треугольники
и кресты окно рисует плоскими фигурами в плане размером в метрах,
и в пакет они идут так же, мешем с `shape`. Линии слоя - часть
`lines` с цветом в вершинах, линии трубами - мешем.

Пакет с точками пишется форматом 2. Читатель формата 1 скажет, что
пакет новее него, а не упадёт на незнакомом примитиве. Пакет без
точек остаётся форматом 1.

Читателю на Rust нужны ключи от `format` до `glb`. `state` он хранит
как есть и при записи возвращает: так пакет, открытый вне QGIS,
снова открывается в QGIS с прежними настройками окна.

Камера окна живёт в координатах просмотра: план сдвинут на центр
сцены, высота умножена на преувеличение. В пакет она пишется
в настоящих координатах (`camera_to_world`), окно на другом
компьютере ставит её под свой центр (`state_for_window`).

`read_glb` в `scene_package.py` читает GLB обратно в части. Это
образец для читателя на Rust и тестовые данные для него же: пакет,
записанный тестом, и его разбор Python дают пары «вход - ожидаемый
итог».

## Приложение сцены на Rust

Раскладка как в PlanetX Lite:

```
isoliner-scene/
  crates/
    scene-format/   чтение и запись .i3dscene, scene.json, GLB
    scene-core/     части, камера, облёт (порт flight.py), короб (axes.py)
    render/         wgpu: тела, линии, прозрачность, освещение
    ui/             окно, список частей, виды, запись видео
  apps/
    isoliner-scene/ отдельное приложение: открыть пакет и смотреть
```

Первая цель: открыть пакет, записанный модулем, и показать то же,
что окно QGIS, той же камерой. Проверка - снимок кадра против снимка
из QGIS при той же камере. Вторая: облёт по видам и запись MP4.
Третья: обрезка и разрез по линии на стороне Rust.

Заготовка - хранилище `C:\Dev\isoliner-scene`: пакет сцены, камера,
облёт, отрисовка, окно и расчёты 2.23 и 2.24 на Rust, сверенные
с модулем. Проверочные данные для него собирает
`tools/make_fixtures.py`: пакет демо, облёт, тела вдоль оси, прогоны
инструментов, `tools.json`. Дальше работа идёт в Claude Code на машине
автора, план - `doc/PLAN.md` там.

## Сцена и инструменты в RustGIS

RustGIS получает два дополнения.

1. Сцена: крейты `scene-format`, `scene-core` и `render` подключаются
   к RustGIS как вид окна. Источник частей там не пакет, а слои
   RustGIS, собранные в те же части.
2. Инструменты: RustGIS читает `tools.json` и строит окна
   инструментов по описаниям. Расчёт каждого инструмента переносится
   на Rust по тексту `tools/<имя>.py`, с тем же кодом, полями
   и выходами. Сверка - те же тесты: вход из `tests/test_tools.py`,
   итог Python против итога Rust.

## Что меняется для пользователя QGIS

Ничего. Имена Processing, поля, подписи, подсказки и переводы
прежние, модели и сценарии с инструментами работают как работали.
Новое в окне просмотра одно: пакет сцены в списке форматов выгрузки.
